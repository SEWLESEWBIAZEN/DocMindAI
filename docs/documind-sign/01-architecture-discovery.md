# DocuMind Sign — 01. Architecture discovery

- **Milestone:** M0 (discovery only; no application code changed).
- **Repository state:** branch `ccr-ac2d5c32-hw6qxt`, 2026-11-28.
- **Method:** reading code, migrations, ADRs and configuration. Every finding below names the
  file it comes from.
- **Purpose:** each prompt-review finding (A1–F2) is confirmed, corrected or extended here.

## 1. Summary

DocuMind already has most of the platform services a signing module needs, so signing can be
built on them rather than beside them:
- workspaces, roles and fixed permissions;
- per-workspace data planes and storage;
- hashed single-use tokens;
- SMTP email;
- Celery with sweepers;
- a rate limiter that can refuse requests when Redis is down;
- an audit log with an outbox for customer databases;
- document upload, processing, indexing and RAG;
- a tested tenant-isolation sweep.

**What's genuinely new:**
- PDF page rendering in the browser;
- writing to PDFs on the server;
- a public portal that works without a workspace session;
- immutable evidence storage.

**Five findings change the design:**

1. **Every data-plane table exists twice** (§4.2). There's one migration set for the shared
   database and one for dedicated and customer databases, and a parity test keeps them identical.
   Every new agreement table needs both.
2. **The orphan reconciler would delete signing evidence** (§5.3). `documind-manage orphans`
   treats any file under `workspaces/{id}/` that no `document_versions` row refers to as an
   orphan, and `--delete` removes it. Agreement files must be registered before the first one
   is written.
3. **"Sender only" visibility needs a restricted collection** (§7.2). A document in no
   restricted collection is visible to the whole workspace. The only existing way to hide a
   document is to put it in a restricted collection.
4. **Workspaces in "customer workers only" mode** (§6.3) don't let DocuMind's workers process
   their files. PDF finalization runs on DocuMind's workers.
5. **Agreement files aren't covered by infrastructure migration** (§4.4). The workspace
   migration copies only files that `document_versions` refers to.

## 3. Document lifecycle today

1. **Upload:** `POST /workspaces/{id}/documents`. The file is validated by its content (and by
   ClamAV if enabled). The original is stored at
   `workspaces/{ws}/documents/{doc}/versions/{ver}`, and `documents` and `document_versions`
   rows are written. `checksum_sha256` is recorded on both.
   - **Duplicates:** a unique index on `(workspace_id, checksum_sha256)` prevents the same file
     being uploaded twice into one workspace (`models/documents.py`).
2. **Processing:** a `processing_jobs` row acts as an outbox, and the Celery task receives
   `(job_id, workspace_id)`.
   - The worker extracts text with PyMuPDF.
   - **Encrypted PDFs are rejected here** (`pdf.needs_pass`, `extractors.py:98`).
   - It writes `document_pages` (text and headings per page, **no word coordinates**) and
     `document_chunks` with embeddings.
   - A sweeper re-queues stuck jobs.
3. **Versions:** uploading a new version creates a new `document_versions` row and
   re-processes. Older versions keep their storage keys, so **a version's file never changes**.
   An agreement can pin `(document_id, version_id)`, plus a snapshot of its own.
4. **Use:** search, answers (`/ask`, conversations), extraction, deadlines, summaries. All are
   filtered by the visibility rule (§7.2).

## 4. Workspaces, data planes and infrastructure

### 4.1 Control plane and data plane

- **Control plane (central database):** users, workspaces, memberships, roles and permissions,
  plans, subscriptions, the audit log, the credential vault, the infrastructure registry, API
  keys, invitations, data exports.
- **Data plane:** the 18 tables in `DATA_PLANE_TABLES`
  (`infrastructure/database/dataplane.py`), from `documents` through `connector_items`.
  - **Shared plane:** for workspaces on DocuMind's defaults, these tables are in the central
    database.
  - **Dedicated or external database:** the tables live in the workspace's own database, in
    schema `documind`. There, workspace references point to a local `tenant_workspaces` anchor,
    and user references become plain UUIDs.
- **Routing:** `InfrastructureResolver.resolve(workspace_id)` returns the data plane's session
  factory and the storage adapter. While a migration is running it raises
  `WorkspaceMigratingError` (503).

### 4.2 Two migration sets

- Shared-plane tables are created by the main Alembic environment (`backend/alembic`, now at
  revision 0023).
- Dedicated and external planes use `backend/alembic_dataplane` (now at `dp0005`), from
  `dataplane_metadata()`.
- A **parity test** keeps the two schemas identical apart from control-plane references.
- **Consequence:** each new data-plane table needs a revision in **both** environments and an
  entry in `DATA_PLANE_TABLES`.

### 4.3 Audit from a data plane

- Data planes write audit entries to `audit_outbox` in the same transaction as the change; a
  relay copies them to the control plane's `audit_logs`.
- `AuditRecorder` (`application/identity/common.py`) records `action`, actor, workspace, target,
  `details`, `ip_address`, `user_agent` and `request_id`.
- **Append-only is a convention, not enforced:** no endpoint edits or deletes audit rows, but
  the database has no triggers or revoked privileges.

### 4.4 Infrastructure migration, backups and exports

| Mechanism | Behaviour | Effect on Sign |
|---|---|---|
| Workspace migration (`application/infrastructure/migration.py`) | Copies the rows of every `DATA_PLANE_TABLES` table in one destination transaction; copies files by listing `document_versions.storage_key` (`_object_keys`); verifies counts; then switches | Rows are copied automatically once registered. **Agreement files are not**: `_object_keys`, `_verify`, `cleanup_source` and `_delete_rows` must learn about them |
| Backups (`infra/backup/backup.sh`) | `pg_dump` of the control database, each dedicated data plane's `documind` schema, and the **whole** bucket | Agreements and files are included automatically |
| Orphan reconciler (`ops/orphans.py`) | Under `workspaces/`, a key is referenced only if a `document_versions` row has it | **Agreement files would be reported as orphans and deleted with `--delete`.** Must be fixed in M1 before any agreement file is written |
| Account data export (ADR 0039, `application/identity/data_export.py`) | Exports the person's conversations and the documents they uploaded, reading each workspace's own data plane | Agreements need a defined export scope (decision C1) |

### 4.5 Account and organization deletion (ADR 0039)

- **Immediate deletion,** no grace period.
- **Account:** organization documents stay, with the uploader set to empty. The audit log keeps
  an entry with the user id.
- **Organization:** everything is deleted. Workspaces on customer infrastructure are refused
  (`409 custom_infrastructure`). Files are deleted after the commit.
- **Consequence:** retention of signing evidence after deletion conflicts with this unless
  explicitly designed (decision C1).

### 4.6 Processing modes

`ProcessingMode = "documind" | "customer" | "hybrid"` (`domain/infrastructure/profiles.py`). In
`customer` mode, DocuMind dispatches no jobs for the workspace (`application/infrastructure/sweeps.py:44`).
A finalization job run by DocuMind's workers would break that promise (see 02 §12).

## 5. Identity, authorization and tokens

### 5.1 Roles and permissions

- **Roles:** owner, admin, member, viewer (`domain/identity/permissions.py`).
- **Permissions:** a fixed `Permission` enum (16 today), seeded into the `permissions` and
  `role_permissions` tables. Later migrations add grants, for example `0004_archive_and_mfa`.
- **Ownership pattern:** `_own` / `_any` pairs, such as `documents.archive_own` and
  `documents.archive_any`. The prompt's "own agreements" for members maps directly onto this.
- **Request context:** `WorkspaceContext` (`domain/identity/policies.py`) carries
  `workspace_id`, `workspace_kind`, `user_id`, `member_id`, `role` and `permissions`. It's
  resolved from the database on every request.

### 5.2 Tokens and one-time codes

- **Tokens:** `domain/identity/tokens.py` has `secrets.token_urlsafe(32)` (256 bits) and
  `hash_token` (SHA-256). Only the hash is stored. Used today for refresh, verification, reset
  and invitation tokens.
- **Email codes:** `mfa_service.py` hashes each code with HMAC and the MFA pepper, checking
  every pepper in the key ring.
- **Links today:** verification and invitation links carry the token in the **query string**
  (`/verify-email?token=…`). The prompt rules that out for signing links (02 §6.2).

### 5.3 Rate limiting

- `RedisRateLimiter` (`infrastructure/ratelimit/redis_limiter.py`) falls back to per-process
  counters when Redis is down.
- Scopes in `FAIL_CLOSED_SCOPES` (today `ai:user`, `voice:user`) are refused with 503 instead.
  Signing-code checks can be added to this set (prompt §10.2).

## 6. Background work and email

### 6.1 Celery tasks today

- processing and its sweep;
- reply sweep and seat sync;
- extraction and its sweep;
- deadline reminders;
- connector sync and schedule;
- Slack answers;
- data export and its sweep.

Beat schedules are in `worker/celery_factory.py`.

### 6.2 Email

- Sent directly through the `EmailSender` port, from services (`mfa_service.py`,
  `deletion.py`) and from workers (reminders, exports).
- No email outbox table.
- Deadline reminders avoid duplicates by recording what was sent on the row itself
  (`deadlines.reminders_sent`).
- Development delivers to Mailpit over real SMTP.

### 6.3 Finalization and processing mode

There's no precedent for DocuMind's workers writing a new file into a customer's bucket for a
workspace in `customer` processing mode. Document processing in that mode is done by the
customer’s workers through the worker API (ADR 0024, MI-7).

## 7. Documents, collections and visibility

### 7.1 Model

- `documents` (with `current_version_id`, `uploaded_by_user_id`, `archived_at`, `is_sample`);
- `document_versions` (`storage_key`, `checksum_sha256`);
- `document_collections` (`restricted`);
- `collection_members`;
- `document_collection_items`.

Children reference parents through composite `(id, workspace_id)` foreign keys, so the database
itself prevents cross-tenant references.

### 7.2 Visibility rule (ADR 0036, `repositories/visibility.py`)

- A document in **no** restricted collection is visible to **everyone** in the workspace.
- A document in one or more restricted collections is visible only to members of at least one
  of them, plus admins and owners (`viewer_of` returns `None` for holders of
  `workspace.update`).
- The rule is enforced in SQL for lists, downloads, pages, search, answers, extraction and
  deadlines.

**Consequence for C4:** a signed PDF can be limited to the sender and participants only by
putting it in a restricted collection whose members are those people. There is no per-document
access list.

## 8. Plans and entitlements

- `domain/billing/plans.py` defines `PlanKey` (free, pro, business, enterprise) and a typed
  `Entitlements` dataclass: limits such as `max_documents` and `chat_tokens`, and features such
  as `byok` and `custom_storage`.
- A migration seeds the `plans` table from this catalog, and a test asserts they match.
- Per-workspace overrides exist.
- Integrations use a different mechanism: a plan set, `INTEGRATION_PLANS`
  (`domain/integrations/api_keys.py`).
- **Consequence for C2:** add `agreements_per_month` and `recipients_per_agreement` fields plus
  a seed migration, or a plan set like integrations.

## 9. Frontend

- **Structure:** `features/*` folders; shared UI in `components/ui` (Button, Menu, Dialog,
  Badge, PageHeader, States, Toast, Field).
- **Pages:** lazy-loaded; workspace pages under `/w/:workspaceId`. Public pages (`/login`,
  `/verify-email`, `/invitations/accept`) sit outside the app shell, which is the right
  precedent for the signer portal.
- **Theme:** design tokens in `styles/index.css`. Light and dark themes; accent
  `--color-accent: #0e7490`.
- **Reusable layouts from the redesign:**
  - viewer: thumbnail rail, toolbar and side panel (`docview`, `reader`, `intel`);
  - library: tabs and filter row;
  - `SettingsTabs`.
- **No PDF rendering library.** `pdfjs-dist` 6.5.438 is Apache-2.0 and needs Node ≥ 22.13;
  the build image is on Node 22, which qualifies.
- **The CSP matters:** PDF.js must load its worker, standard fonts and character maps from the
  same origin, with `isEvalSupported: false`. No CSP change should be needed; to be verified.

## 10. Tests and verification infrastructure

- **Backend integration tests** run against real PostgreSQL + pgvector, Redis, MinIO and
  Azurite (`backend/tests/integration`). Live tests are opt-in.
- **Tenant isolation sweep** (`test_tenant_isolation_sweep.py`): reads every workspace-scoped
  operation from the app's OpenAPI document. **New `/workspaces/{id}/agreements…` routes are
  swept automatically.** The public signing routes need their own tests (prompt §10.4).
- **Contract test:** the OpenAPI contract test plus generated TypeScript types.
- **Browser tests:** Playwright against the development stack (30 tests); Mailpit is reachable
  from tests.
- **Production smoke stack:** `deploy/production/smoke`.
