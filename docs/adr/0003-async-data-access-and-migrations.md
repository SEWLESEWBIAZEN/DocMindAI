# ADR 0003: Async SQLAlchemy + asyncpg, Alembic, pgvector in the primary database

- Status: Accepted
- Date: 2026-11-23

## Context

The API is I/O bound (database, Redis, S3, LLM streaming over SSE). The
specification requires PostgreSQL with pgvector for both relational and vector
data, plus Alembic migrations.

## Decision

- **SQLAlchemy 2.x async ORM with asyncpg.** One engine per process with
  bounded pool settings and `pool_pre_ping`. Sessions are created per unit of
  work from an `async_sessionmaker(expire_on_commit=False)`.
- **Alembic with an async `env.py`.** The URL comes from application settings,
  never from `alembic.ini`. `-x database_url=` targets other databases (tests).
- **pgvector in the same PostgreSQL instance.** Tenant filters
  (`workspace_id`) and vector similarity run in a single SQL query, which
  satisfies the requirement that tenant filtering happens in the database,
  not after retrieval.
- The `vector` extension is created by the Compose init script (as superuser)
  and idempotently by migration `0001`.
- A deterministic constraint naming convention keeps autogenerated migrations stable.

## Alternatives

- *Dedicated vector database (Qdrant, Weaviate):* tenant filtering and
  consistency would span two systems, and it is another service to operate on a
  single VPS. Revisit only if load testing shows pgvector (HNSW) is insufficient.
- *SQLModel:* thinner abstraction, but lags SQLAlchemy features and mixes API
  schemas with persistence models.
- *Sync SQLAlchemy in a threadpool:* simpler, but it wastes threads during long
  SSE streams.

## Consequences

- Celery tasks (sync by default) will need either an async bridge or a small
  sync engine. Decided in Phase 4.
- In production the application role should not be a superuser. The extension
  is then pre-created by an administrator (Phase 10 runbook).
